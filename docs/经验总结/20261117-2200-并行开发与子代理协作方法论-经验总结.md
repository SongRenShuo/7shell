# 并行开发与子代理协作方法论汇编

> 本汇编收录自 mybatis-plus-sql-visualizer 仓 `docs/经验总结/` 五篇方法论文章的普适核心（2026-09~10 实战沉淀，与具体技术栈无关），建仓时一次性导入。叙事细节与完整案例查源仓原文。
> 配套规则见 [`docs/开发流程-派活与验收清单.md`](../开发流程-派活与验收清单.md)；本篇只写「为什么」，不重复「怎么做」。

## 一、多路并行开发中的验证盲区（为什么绿灯看不出问题）

四类「绿灯看不出的问题」：

1. **加了防护不等于防护有效**——须有「防护被绕过」的反例（反向验证）。
2. **加了透传不等于透传到达**——须向上找同函数的外层吞噬点。
3. **追加字段会挤掉老信息**——断言被挤掉的字段仍可见。
4. **接线守卫用整文件 contains 会假绿**——必须匹配调用点精确串；整文件子串检查在回退调用后仍然绿。

守卫自证盲区四条方法论：

- 守卫改动必须用真实站点做「删掉修复 → 必红」。
- 合成样本证明规则不空转，真实站点反向验证证明规则有判别力，**不可互替**。
- 「仓内 0 违规」在写命中为 0 时是空绿。
- 守卫绑定面要覆盖仓内主流形态——新规则上线前先 grep 要防的真实站点用哪种写法。

「根治的口径怎么被证伪」：声称根治前先问「我的改动是否触及机制本身」。

## 二、子智能体后台派发与并行调度

- **并行度来自「后台」**，与「一条消息塞几个调用」无关（一条消息多个调用实测只产出一个，一律 run_in_background 逐条派）。
- **派发前三检查**：①写集显式声明并两两求交——交集非空必须串行，同文件三处改动合成一个 agent；②主任务自留一条不重叠车道，不空等；③prompt 自包含——后台 agent 无法提问，不确定先派只读侦察。
- **收口协议**：不轮询等通知；读产物不读 agent 输出全文；回报压缩为「状态/产物/证据/是否通过」；写与验分离，另派只读复核；**拿 agent 自述当结论是最常见的坑**。

## 三、测试三档分层与收口时序

- 为什么子代理不该跑全量：并行期读数不可信（别人在途改动让全量成片失败）、墙钟 N 倍、构建校验的判别力不随次数增加。
- 收口时序「门禁 ∥ 写文档」：全部子代理完成后单派只读收口代理跑全量，主控同时写文档收尾，并行不空等。
- 长命令一律后台不许 sleep：睡几百秒既解决不了锁又白占并发槽位。
- 待办清单与实际进度同步：清单是用户看进度的唯一窗口，不许出现「实际做完好几步、清单停在第一步」。

## 四、token 消耗治理（省 token 的主杠杆是会话粒度，不是提示词）

- 一条工具输出进入上下文后每次请求重发：早收口收益是**乘法级**。成本模型——第 k 次请求的一条 5K 输出，若会话还有 100 次请求，实际消耗 500K。
- **P0 纪律**：上下文到 12~15 万就收口、写交接文档、开新会话；一个可提交单元一个会话；探索交给子代理、只回收 ≤1.5K 结论。
- **交接文档字段固定**：分支与 tip / 已完成 / 未完成 / 证据读数 / 下一步 / 踩过的坑。
- 红线：截断只截通过时的噪音；失败必须走结构化失败聚合，不能盲截栈。

## 五、调度模式与决策模式的选用

- 一句话判定：**有执行疑问（怎么分配、并行还是串行）→ 开执行调度层；有方向/因果/分歧疑问（该不该做、为什么、选哪条路）→ 开决策统筹层**。
- 方向未定就并行，方向错了并行越多错得越多。
- 组合用法：决策层主持总循环（定位—复盘—转失败），调度层在每轮里战术性并派与复核。
