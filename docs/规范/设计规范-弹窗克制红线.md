# 弹窗克制红线

> 本文档固化 7shell 弹窗与通知的设计红线：什么能弹、什么不能弹、新弹窗合入前要过哪几问。机制导入自 mybatis-plus-sql-visualizer 仓同名规范。
> 立项依据：赛道内最完整的同类工具曾因「平均一小时一次弹窗」被用户打出 1 星并弃用——同类评论三年内出现三次。7shell 的「零打扰」不能只隐含在实现里，要写成约定，防的是未来迭代中「顺手」加一个无门禁弹窗。

**清单与代码漂移的教训已吸取（源仓实测：文件级行号清单随重构大面积漂移失效）**：本规范从第一天就把触点清单写成「grep 模式 + 门禁机制字段」，不写文件:行号。每次触碰弹窗相关代码后重跑一遍：

```bash
# 前端（Vue3 + Tauri dialog/notification）
rg -nE "window\.(alert|confirm|prompt)|\\b(ask|confirm|message|open)\\s*\\(|ElMessageBox|MessageBox|notification\\." apps/desktop/src --type ts -g '*.vue'
# Tauri 后端与 Rust 侧弹窗/通知
rg -nE "plugin-dialog|tauri-plugin-notification|MessageBox|Notification" crates/ src-tauri/
```

模式本身随技术栈演进修订；修订模式也是一次登记。

## 登记义务

新增或移除任何弹窗/通知触点，须同步更新本文触点清单；清单与 grep 结果对不上时，以 grep 复核结果为准并修订本文。
新增「应用主动」类触点除登记外，还须过下方准入五问，任何一问不过不得合入。

## 触点清单

> 基线：待首审。7shell 尚未做过触点审计，首次合入弹窗相关改动时先跑一遍上面的 grep 建立基线行数，再逐点定性登记。

| 触点 | grep 命中模式 | 触发方（用户/应用主动） | 门禁机制（开关/一次性/频率上限） |
|------|--------------|------------------------|--------------------------------|
| 工作台电源确认对话（WorkbenchPane.vue，重启/关机前的后果确认） | `ConfirmDialog` 组件复用；`window.(alert\|confirm\|prompt)` 0 命中（2026-11-18 linuxdesk 实施时复核） | 用户主动（点击重启/关机按钮） | 每次点击一次确认，无自动弹出；后端另有 policy 矩阵门（destructive 至少 ask）与审计行，双闸独立 |
| 工作台操作回执/错误 toast（电源下达回执、POLICY-DENIED 失败提示） | toast 既有通道复用，无新增通知组件 | 用户主动（操作的结果回执） | 仅伴随用户操作出现，无主动推送 |

## 允许类

默认放行，不需要额外论证，但仍须登记进触点清单。

1. 用户操作反馈：点击按钮后的结果、错误、「未找到」类提示。
2. 用户操作确认：破坏性操作（删除会话/主机、清空数据等）的确认框、轻量输入框。
3. 含开关的一次性通知：默认关或可永久忽略，同一触点每会话至多一次。

## 禁止类

一律不做，Code Review 按此驳回。

1. 无开关的应用主动弹窗、导流弹窗。导流只走设置页与 README。
2. 营销/评分引导弹窗。评分引导只进 README 与更新通知正文链接。
3. 频率超限的任何主动触点，超出「每会话一次」即违规。
4. 后台失败转弹窗。连接失败、下载失败等主链失败在面板内报错或静默降级重试，不弹模态框。

边界判断：「用户点击直接引发」是允许类的客观判据。拿不准的触发路径（如异步回调里弹提示）按禁止类处理，宁紧勿松。

## 准入五问

新增主动触点前逐问自检，全部通过才准合入：

1. 是否用户点击直接引发？
2. 面板内或通知形态是否确实不够用？
3. 是否带开关或一次性？
4. 频率上限是多少？
5. 是否已在本文触点清单登记？
