# 文档命名规范（内部协作文档）

> 约束 7shell 仓内部协作文档的命名与组织。机制导入自 mybatis-plus-sql-visualizer 仓同名规范，删去其业务专属节。
> 分工边界：面向用户的英文文档（`docs/guide/`、`docs/index.md` 等 VitePress 站点）不归本规范管；本规范只管「我们怎么做事」的内部协作文档。与 [`docs/pips/`](../pips/README.md) 的分工见 §三。

## 一、时间戳前缀命名体系

一次性任务文档统一 `{YYYYMMDD}-{HHMM}-{主题}-{文档类型}.md`，按类型归目录：

| 类型 | 目录 | 示例 |
|---|---|---|
| 开发计划 | `docs/开发计划/` | `20261117-1430-连接重连策略-开发计划.md` |
| 调研报告 | `docs/调研报告/` | `20261117-1617-竞品横向对比-调研报告.md` |
| 验收文档 | `docs/验收文档/` | `20261117-1225-里程碑验收-验收文档.md` |
| 性能分析 | `docs/性能分析/` | `20261117-0821-启动耗时-性能分析.md` |
| 经验总结 | `docs/经验总结/` | `20261117-0900-门禁提速-经验总结.md` |

- 日期 YYYYMMDD、时分 HHMM（文档创建时刻）。
- 验收文档的内容要求：一次交付（合并/里程碑/发行）带来的全部用户可见变更集中验收——新增功能清单、逐项验收步骤（操作路径 + 预期结果）、已知边界、回归基线；自动化已验证项与需手工走查项分开陈述。
- 经验总结的范围界定：跨任务可复用的踩坑与配方；单任务的实施过程记录写在开发计划文档的实施记录节，不另立经验总结。

## 二、规范类四后缀

`docs/规范/` 目录下，主题**不带日期**（约定长期有效，不按任务归档）：

- `{主题}-规范.md`——约定类
- `{主题}-清单.md`——可勾选验收项
- `{主题}-红线.md`——禁止项
- `{主题}-说明文档.md`——长期说明（机制、指南、协议）

确需区分版本时写 `{主题}-{YYYYMMDD}版.md`。一次性任务材料不得放入 `docs/规范/`。

**根级账本例外**：两类文件留 `docs/` 根目录、不进 `规范/`——
- `docs/LESSONS.md`：活跃教训账本，收口/故障后高频追加，位置服务于写入入口（与 `AGENTS.md` 呼应），不是稳定规范。
- `docs/MEMORY.md`：文档检索索引，索引入口身份要求路径长期稳定。

判据：**「稳定规则/约定」进 `规范/`；「活跃账本/索引入口/权威总册」留根**。

## 三、与 PIP 的分工

- 大提案（动 security-model 不变量、公开契约、crate 依赖方向、发行承诺）走 [`docs/pips/`](../pips/README.md)，命名 `PIP-NNNN-short-title.md`（其 README 的门槛与流程为准）。
- PIP 管「决策为什么这么做」；时间戳计划文档管「一次实施怎么干活、干到哪了」。两者可并存：PIP-Accepted 后的实施细节立时间戳计划文档，互相链接不复制内容。

## 四、引用与图片规范

- 文档内嵌图一律使用**文件相对路径**（基准=当前文档所在目录）——这是唯一在 GitHub / Gitee / VS Code / IDE 预览中全部正确的写法；禁内嵌外链图片（防盗链 302 会导致站外不可见）。
- 资源清单类表格里列「路径」时用仓库根相对写法（描述文件位置而非嵌入）。
- 手工渲染的示意图（非真机截图）在引用处必须**显式标注「设计稿，非实现截图」**，避免被误读为功能已实现。
- 对外素材（README/官网引用的图）与开发过程设计稿分目录存放，防清理时误删对外图。
- 功能演示动图不入仓：README 引用官网稳定 URL，仓库内不留副本。
