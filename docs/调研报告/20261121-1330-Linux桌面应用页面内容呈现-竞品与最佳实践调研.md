# Linux 桌面应用页面内容呈现——竞品与最佳实践调研

日期：2026-11-21
范围：Linux 桌面工作台全部应用窗口（监控/系统信息、系统面板、主目录、终端、Docker、传输、转发、服务、日志、批量、回收站）与桌面 widgets 的**内容呈现层**——图形化、信息层级、密度、空/加载/错误三态。功能逻辑不在本报告范围。
方法：只读调研。代码侧逐组件盘点（`apps/desktop/src`，事实带 file:line）；外部侧以各家官方文档与设计系统为一级来源，每条事实随 URL。与 [界面视觉现状盘点](20261118-0300-界面视觉现状盘点-调研报告.md) 的关系：那份盘的是「样式基础设施」（token/字号/按钮/动效），这份盘的是「每个页面里内容该怎么摆、该不该变成图」；两份互不重复。

## 结论速览

1. **本桌面「监控」窗口是全桌面对标差距最大的一页**：窗体（`components/inspect/SystemReport.vue`，249 行）是纯文字表格页——系统信息 dl 表、CPU 型号表、CPU 占比数字表、内存/swap dl 表、网卡表、磁盘表，整页无一张图、无一根条。而它就是桌面「监控」与「系统信息」两扇门的宿主（`WorkbenchPane.vue:1883-1889`）。用户「特别是监控要图形化」的判断在代码上完全成立。
2. **竞品共识一：概览优先，下钻随行**。Grafana 官方最佳实践要求仪表盘「讲一个故事、回答一个问题」，分层组织、支持 drill-down（[grafana best-practices](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/best-practices)）；Netdata 用 summary tiles 把每个分区压成「一眼可读的瓦片」，图表之上再铺异常带（[netdata 1.39 charts v3](https://www.netdata.cloud/blog/netdata-version-1.39)）；btop 用盒子围栏把 CPU/内存/网络/磁盘分组速览，htop 用彩色条组呈现每核占用（对比结论来自本轮搜索综述，可查证实锚：[Glances 项目页](https://github.com/nicolargo/glances)、[htop 项目页](https://htop.dev/)）。映射到本仓：每个应用窗打开的第一屏应是「状态带」（可用 stat tile/环形图），清单与明细留在下滚。
3. **竞品共识二：色彩即语义，阈值三档**。Grafana 阈值默认 `Base=green`、`80=red`，可加中间档形成绿→橙→红色梯（[configure-thresholds](https://grafana.com/docs/grafana/latest/visualizations/panels-visualizations/configure-thresholds/)）；stat 面板支持按阈值染数值或染背景（[stat](https://grafana.com/docs/grafana/latest/visualizations/panels-visualizations/visualizations/stat/)）。本仓已有完整对等物：`usageTone` 90/95 两档阈值（`lib/workbench/desktopWidgets.ts:56-63`）+ `--success/--warning/--destructive` 双主题令牌（`globals.css:39-41/165-167`），但图形层几乎没人消费——阈值纪律「有 token、无图形」。
4. **竞品共识三：数字永远 tabular、单位永远随值**。Grafana 把「必须标单位」列为硬规则（best-practices 页）；排版文献的结论是 `font-variant-numeric: tabular-nums` 让数字对齐防抖动，且**不要**把整个界面换成等宽字体（[tabular numbers in CSS](https://dev.to/alanwest/tabular-nums-in-css-font-variant-numeric-vs-monospace-hacks-25cn)、[MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/font-variant-numeric)）。本仓 widgets 已用 `tabular-nums`（`WorkbenchWidgets.vue:428`），但大多数数值页用 `font-mono` 整体等宽——文字也被拉成等宽，浪费横向空间（在 320px 侧栏里尤其贵）。
5. **图表选型有一个现成的内部矛盾**：`MonitorSpark`（`components/monitor/MonitorSpark.vue`）用**条**画离散采样并在注释里说清了理由——「line 暗示采样之间的值也被测过，而它们没有」；而 `StatSparkline`（`components/container/StatSparkline.vue`）用**折线**画同样离散的 5s 采样。Stephen Few 的判据站在 MonitorSpark 一边：趋势上下文用 sparkline、连续时间序列用 line、离散区间/类别比较用 bar（[Few 框架综述](https://www.datarocks.co.nz/blog/data-viz-bookshelf_show-me-the-numbers-stephen-few)、[Atlassian chart types](https://www.atlassian.com/data/charts/essential-chart-types-for-data-visualization)）。收敛成一个图表词汇层时，这是必须裁决的点。
6. **空/加载/错误三态的分档标准直接可用**：NN/g 的分档是 <1s 不画指示器、2-10s 用骨架（整页）或 spinner（单件）、>10s 用进度条；骨架必须镜像最终结构（防布局跳动），且「只有框架没有占位块」的骨架等于没有（[NN/g skeleton screens](https://www.nngroup.com/articles/skeleton-screens/)）；空态=解释+行动入口，永远不是 loader（[loading-state 分辨](https://kompassify.com/blog/loading-state-ux-guide)）。本仓现状：39 个文件以转圈为唯一等待语言、skeleton/pulse 仅 7 处（[现状盘点 §3.3](20261118-0300-界面视觉现状盘点-调研报告.md)），表格空态是一行灰字（`lib/table.ts` emptyCell）。
7. **布局科学的可执行三条**：F-pattern——关键读数放首屏左上、沿左缘对齐（[IxDF visual hierarchy](https://ixdf.org/literature/topics/visual-hierarchy)、[NN/g](https://www.nngroup.com/articles/visual-hierarchy-ux-definition)）；8px 间距网格 + 卡片内部结构统一（头/值/图/脚），用列跨度变化而非任意宽度制造层级；层级靠尺寸/对比/位置/留白四杠杆，不靠加框加线。设置/表单类密度参照 Apple/GNOME 的 sidebar+detail 分栏与分组列表（[Apple HIG sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)、[GNOME HIG](https://developer.gnome.org/hig)）。
8. **不引入图表库是正确裁定**：本桌面的全部序列都是 30~60 点、2s/5s 节奏（`dockerMetrics.ts:12-15`、`stores/monitor.ts:84`），uPlot 的性能优势（3,600 点 60fps 下 10% CPU vs Chart.js 40%，[uPlot 基准](https://github.com/leeoniya/uPlot)）完全用不上；canvas 系库吃不了 oklch `var()` 色板（每帧取色要 JS 解析），与「令牌单一来源」（`WorkbenchPane.spec.ts` 守卫的 `--workbench-*` 派生链）直接冲突。手写 SVG 是对的，缺的只是**收敛**：现有 3 种图形原语（MonitorSpark 条、StatSparkline 线、SystemPanel 环）互不复用。历史长序列（>5 分钟）若立项，再评估 uPlot。

### 1.2 图形原语与数据底子

- **MonitorSpark**（monitor/）：div 条形一排，多序列共享峰值缩放，高 40px（`h-10`），注释明确「条不冒充连续」。

### 1.3 令牌底子（globals.css）

- 语义色双主题齐备：`--success/--warning/--destructive/--info`（:39-41 亮、:165-167 暗）；桌面 chrome 有 `--workbench-warning/--workbench-danger`（widgets 在用）。

## 2. Grafana：面板网格与阈值色彩的教条

**做得好的（官方文档逐条）**：

- **叙事与层级**：仪表盘回答一个具体问题；数据从大到小、从总到分排布；分层 drill-down（rows 收纳明细）；一 row 一服务（[best-practices](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/best-practices)）。
- **stat 面板的自动布局**：按可用宽高自动排布、面积型 sparkline 画在数值背后（Graph mode=None/Area）、按阈值染数值或背景（Value/Background Gradient/Solid）、无值默认画连字符（[stat](https://grafana.com/docs/grafana/latest/visualizations/panels-visualizations/visualizations/stat/)）。「无值画 —」与本仓 MonitorPanel 的空态哲学（dash 而非零）完全同源。
- **阈值即色彩语义**：Base=green、超限=red、可加 warn 中间档；Absolute/Percentage 两模式（[configure-thresholds](https://grafana.com/docs/grafana/latest/visualizations/panels-visualizations/configure-thresholds/)）。
- **单位与坐标纪律**：每个图必须标单位；不同单位/量纲的双轴才用左右轴；CPU 归一化成百分比而非原始核数。
- **刷新纪律**：数据小时级变化就别 30s 刷新——本仓「无人观看不采样」的纪律是同一思想的更严格版。
- **堆叠图慎用**：stack 会互相掩盖，多数场景关掉。

**映射到本仓**：stat tile（大数字+阈值染+背景 sparkline）是监控窗口、widgets、Docker 概览的公共母版；「rows 收纳」对应 SystemPanel 七分区与 SystemReport 的分区结构；「标单位」对应 perSecond/formatSize 已有、但图形轴缺。

**要避免的**：为了满而堆满（Grafana 社区反复强调 keep it clean）；一屏多量纲混杂；把表格当装饰。

## 3. 终端仪表：htop / btop / glances / Netdata

- **htop**：彩色化的 top——per-core CPU 条、内存/swap 条、load/uptime 读数一眼可扫；对比对象 `top` 默认单色、要按 `1` 才能看每核状态，正好反证色彩与分组的价值（[htop 项目页](https://htop.dev/)；对比结论来自本轮搜索综述，原文经聚合返回未逐字复核）。
- **btop**：盒子围栏把 CPU/内存/网络/磁盘围成分组面板，密度高但**靠分组不靠拥挤**；主题、显示的 meters、排序都可持久化（结论来自本轮搜索综述；可查证实锚为 [btop 仓库](https://github.com/aristocratos/btop)）。「用户布局偏好要活过重启」是四款工具的公约数。
- **glances**：一个界面全量速览 + 可导出；缺点是资源占用重（[GitHub](https://github.com/nicolargo/glances)）——对本仓的启示是**采样纪律**要严格（已做到）。
- **Netdata**：把「概览」做成 summary tiles（每分区一张瓦片，[v1.40](https://learn.netdata.cloud/)），每张图上方铺异常率带（[v1.41 anomaly ribbons](https://www.netdata.cloud/blog/netdata-version-1-41-anomaly-advisor)），图表引擎完整重构过一轮（[charts v3](https://www.netdata.cloud/blog/netdata-version-1.39)）；其自称的差异点是「每张图都可交互下钻」。

**映射到本仓**：监控窗口第一屏应为「tiles + 条带」构图（htop 的构图 + Grafana 的 stat）；widgets 就是桌面的 summary tiles，缺的只是每卡一根趋势条（Netdata tile 的最小形态）。**要避免的**：btop 式的字符画密度——Web 字体渲染没有等宽网格兜底，密度失控就是滚动失控；Netdata 式的「每图 25 个交互点」——SSH 客户端的监控页是速览不是工作站。

## 4. 容器控制台：Docker Desktop / Portainer / K9s / Lens

- **Portainer**：容器详情页的 Stats 视图给 CPU/内存/网络 RX-TX 三张实时图（[docs](https://docs.portainer.io/user/docker/containers/stats)）；但**没有**全部容器的资源总览——用户被迫配 Prometheus+Grafana（[r/portainer 讨论](https://www.reddit.com/r/portainer/)）。本仓的 Docker 概览页已经有引擎级三序列，比 Portainer 的起点高；差距在**容器列表行内没有迷你读数**（列表只看状态不看负载）。
- **Docker Desktop**：容器页本体不放资源图，资源图在 Resource Usage 扩展里给 CPU/内存/网络/磁盘四组曲线（[官方博客](https://www.docker.com/blog/how-to-monitor-container-memory-and-cpu-usage-in-docker-desktop)）；CLI `docker stats` 的列口径是 CPU%、MEM USAGE/LIMIT、NET I/O（[docs](https://docs.docker.com/reference/cli/docker/container/stats/)）——「USAGE/LIMIT」的分子分母呈现值得抄。
- **Lens**：集群概览页用资源环/仪表（CPU、内存、pod 状态）做第一屏，是「打开即状态」的范本（[lenshq.io](https://lenshq.io)）。
- **K9s**：终端 UI，键盘驱动、低开销，但没有仪表层——恰好划出「表格控 vs 仪表控」的边界（[k9scli.io](https://k9scli.io)）。

**映射到本仓**：Docker 概览三行（容器/镜像/异常）应升格为带计数的 stat tile + 每张 sparkline 加面积填充与单位；容器列表加一列内存迷你条（数据 `container.stats` 已有）。**要避免的**：Lens 的 Electron 重仪表盘野心——本桌面单连接场景不需要集群级聚合。

## 5. 布局科学：打开即舒适的三条硬规律

- **F-pattern**：文字密集界面用户的扫描是「两横一竖」——首屏左上是注意力的最大份额，沿左缘下行找锚点（[IxDF](https://ixdf.org/literature/topics/visual-hierarchy)、[NN/g visual hierarchy](https://www.nngroup.com/articles/visual-hierarchy-ux-definition)）。落到本仓：每窗第一屏的左上应是「这个应用现在怎么样」（状态 tile/摘要行），不是「这是这个应用的名字」。
- **层级四杠杆**：尺寸、对比、位置、留白。竞品仪表盘的层级不是画出来的（多加边框/线），是**留白分组**出来的——组内 8px、组间 16-24px 的节奏比任何分隔线都干净（四杠杆结论出自上面两条 NN/g 与 IxDF 来源；8px 网格为通行实践结论，本轮未单独溯源到一级文献）。
- **卡片节奏**：卡片内部结构统一（头/主值/图/脚四段），宽度用列跨度（2/3/4 列）变化表达重要性，不用任意宽度；`grid-cols-[repeat(auto-fit,minmax(18rem,1fr))]`（DockerOverview 已用）是正确的自适应基底。
- **设置/表单密度**：Apple/GNOME 的设置页是 sidebar+detail + 分组列表 + 行高一致的三段式（[Apple HIG sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)、[Layout](https://developer.apple.com/design/human-interface-guidelines/layout)、[GNOME HIG](https://developer.gnome.org/hig)）——SystemPanel 的分区导航已经是这个形态，缺的是分区内容的「分组容器 + 留白」而非新的导航。

**要避免的**：首屏塞满（F-pattern 的对面是「全是重点=没有重点」）；任意宽度的瀑布卡；靠 1px 线代替留白分组。

## 6. 图表选型与数字格式化

**选型判据（Few 框架）**：

| 数据形态 | 正确图形 | 本仓对应 |
|---|---|---|
| 此刻的单值 KPI | stat tile（大数字+可选阈值染） | 缺——监控/服务/转发页全是小字数字 |
| 带趋势上下文的单值 | stat + 背景 sparkline（面积） | widgets 缺；Docker 概览有折线无面积 |
| 离散采样的速率（2s/5s 节奏） | **条**（bar-per-sample），多序列共享峰值 | MonitorSpark 对；StatSparkline 错（line 冒充连续） |
| 连续长序列（百点以上、可缩放） | 折线/面积图 | 本仓当前不存在此场景（60 点封顶） |
| 容量占比（磁盘/内存） | 环或水平条+阈值染 | SystemPanel 环对；表格页的 percent 列裸奔 |
| 类别比较（每核、每容器、每接口） | 水平条组或迷你条列 | 缺——CPU 占比是一行数字（SystemReport:140-164） |
| 离散区间的缺口语义 | micro bar（条能表达「没采样」） | Few：line 的缺口会误导（[Perceptual Edge 综述](https://www.vizuiblog.com/blog/sparkline-chart-what-it-is-and-when-to-use-it)） |

**色彩语义**：ok/warn/crit 三档全仓只有一个源头（usageTone 90/95），图形必须消费它而不是各画各的（[Grafana thresholds](https://grafana.com/docs/grafana/latest/visualizations/panels-visualizations/configure-thresholds/)；状态色永不换位的纪律见 [PatternFly status & severity](https://www.patternfly.org/patterns/status-and-severity)）。色盲兜底：Carbon 要求形状+颜色双编码（[Carbon status indicators](https://www.carbondesignsystem.com/building-blocks/core/patterns/status-indicators)）——条/环之外至少留数字可读。

**数字格式化**：`formatSize`/`perSecond` 已统一 K/M/G 口径；缺的是排版规则——数值列与动态读数一律 `tabular-nums`（防抖动、对齐），`font-mono` 退回给路径/命令/代码（[dev.to](https://dev.to/alanwest/tabular-nums-in-css-font-variant-numeric-vs-monospace-hacks-25cn)、[MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/font-variant-numeric)）；单位永远随值出现（Grafana 硬规则），不出现裸 `83` 。

## 7. 空/加载/错误三态的分档标准

- **加载分档**（[NN/g](https://www.nngroup.com/articles/skeleton-screens/)）：<1s 不画任何指示器（闪一下反而烦）；2-10s 整页用骨架（占位块必须镜像最终结构，防布局跳）；单件等待用 spinner；>10s 用进度条。「只有外壳没有占位块」的骨架=没有骨架。
- **空态**：解释为什么空 + 一个行动入口，永不是 loader（[Kompassify](https://kompassify.com/blog/loading-state-ux-guide)）；本仓的哲学底子极好——MonitorPanel 的「空列不是零」、SystemPanel 的「分区答不上来就用一句话说」——缺的只是**统一样式**（现在是每页手写一行灰字）与**行动入口**（空态里应该有「去连接/去创建」的按钮）。
- **错误态**：本仓已统一 destructive 横幅 + 等宽错误码（MonitorPanel:246-255、WorkbenchDockerWindow:75-87），且错误码可选中——这是对的，保持。要补的只是「错误态也留行动」（重试按钮已存在于 Docker 窗，其他页没有）。
- **我们的参照系内已有标准件**：fnOS 拆解记录过 Empty 组件五插画 ×双主题 ×三档尺寸（[fnosUI 精华拆解 §C](20261119-0302-fnosUI精华拆解-调研报告.md)）——本仓不必上插画（违反工具克制），但「空态是一种组件、不是一段文案」的组织方式值得照搬。

## 精华清单 Top 12

1. 监控窗口从纯文字表升为「stat tile 行 + 条带图形区」，这是本期最大单点收益。
2. 一切百分比/容量图形消费 `usageTone(90/95)` + `--success/--warning/--destructive`，全仓一个阈值源头。
3. 离散采样的速率图用**条**不用折线——MonitorSpark 的注释就是裁决书；StatSparkline 应换形态或改名为面积趋势。
4. 数值排版双轨制：数字 `tabular-nums`，`font-mono` 只留给代码/路径/命令。
5. 单位永远随值（`%/s/MB`），裸数字是缺陷。
6. stat tile 的公共母版：大数字 + 阈值染 + 可选背景 sparkline（Grafana stat 的三要素）。
7. 首屏左上放「现状」，清单与明细下滚（F-pattern）。
8. 分组靠留白节奏（组内 8px、组间 16-24px），不靠加线加框。
9. 加载三档：<1s 不画、2-10s 骨架（镜像结构）、单件转圈；骨架必须防布局跳。
10. 空态=一句话解释 + 行动按钮，统一成组件而不是各页手写灰字。
11. 前端已有 60 点 ×2s 历史底子——CPU/内存 sparkline 不需要 Rust 也能落地；>5 分钟历史才需要引擎侧采样。
12. 不引入图表库：30~60 点的量级 + oklch 令牌链路 + CSP 纪律，手写 SVG 收敛成共享词汇层才是正解；uPlot 留给「历史长序列」立项时再评估。
