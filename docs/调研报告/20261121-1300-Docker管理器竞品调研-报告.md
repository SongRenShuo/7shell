## 结论速览

1. **这条赛道上没有「单一赢家功能」，而是三类完成度范式**：管理面板型（Portainer/1Panel/宝塔/群晖/某国产 NAS——全资源域 × 全生命周期）、专精工具型（Dozzle/ctop/dry/Lazydocker——把一件事做到极致）、编排自动化型（Dockge/Komodo/Fleet/Watchtower——让容器自己跟上定义）。7shell 的桌面 Docker 窗口骨架已是管理面板型，缺的是三类各自的「完成度皮肤」：批量与状态自动跟进（管理面板型的尾部）、日志/统计的深度（专精型的头部）、compose 为中心的重建流（编排型的主干）。
2. **最值得抄的十件事**（按杠杆排序，详证见各节）：① 列表多选批量操作（Docker Desktop/Portainer 全员标配，我们零）；② 容器「一键重建/升级」流——Inspect 抓旧参数 → 停 → 拉 → 按原参数重建（Portainer Duplicate/Edit+Rebuild、1Panel `container/upgrade`、群晖映像检查更新、某国产 NAS 更新 5 步确认，四家同构，我们已有 5 步更新确认 + clone 预填，只差「升级=拉新镜像+重建容器」这最后一跳）；③ compose 项目为中心的编辑器与实时输出（Dockge 的立身之本：编辑→保存→up→输出实时流回）；④ 日志搜索三件套：正则/关键词高亮 + Enter 跳转 + 多容器过滤（Docker Desktop），以及 Dozzle 的 SQL 查日志、分屏多日志；⑤ `docker events` 事件流驱动列表自动刷新（dry F9、Dozzle/Portainer 的实时性根源，我们现在是纯手动 refresh）；⑥ 磁盘占用一页清（dry F8 `docker df`、Lazydocker prune 全家桶、1Panel/容器/镜像各自 prune、Docker Desktop Builds 页）——我们只有 image prune；⑦ 镜像加速源/代理的「设置」而非「只读卡片」（某国产 NAS 加速源拖拽排序 + 代理表单、群晖注册表设置、1Panel setting/mirror——我们的 RegistryCard 是刻意的只读事实卡，该升级成受控写入）；⑧ 每容器应用图标（Dozzle 从 homarr/dashboard-icons 取材，品牌识别成本极低收益高）；⑨ 全局快搜（Docker Desktop header 快搜跳容器/镜像/卷；dry 命令面板 `:`）；⑩ 健康状态一等公民：compose ps 的 health、容器 healthcheck 徽标、异常计数进入概览健康灯（我们 engineHealthy 只看 dead/error，不看 health 字段——引擎也未解析）。
3. **明确的「不抄」**：Rancher/Fleet 的多集群 GitOps 重量级模型（K8s 域，与单机桌面场景错位）；Shipwright（经核实是 K8s 镜像构建框架而非 Docker 管理 UI，不同类）；Yacht（模板思路可抄，其自身已停滞、alpha 定位是反面教材）；Portainer BE 的重量级企业层（RBAC/审计/边缘代理——我们单用户桌面形态暂无此需求）；Docker Desktop 的 AI/Gordon 与云 Offload（不同赛道）；Kitematic（已归档）。
4. **Watchtower 已死，思想活在各家 UI 里**：containrrr/watchtower 已宣布停止维护（README 顶部声明，讨论 #2135），活跃续作为 nicholas-fedor/watchtower（4.9k stars）。原生的「定时拉新镜像按原参数重建」能力，在我们这里的正确落点不是做守护进程，而是把已有的「检查更新 → 5 步确认 → pull」手动流补上「重建容器」终点，并留出后续「计划任务」档位。
5. **信息架构上我们已与对标 NAS 子应用对齐**（五页签 + 计数徽标 + 能力位裁剪），差距集中在**深度**而非广度：镜像页没有 tags/层管理入口、容器详情无 stats 选项卡（监控另开对话框）、Compose 页没有 YAML 编辑器（只有新建上传路径）、网络页无详情抽屉、卷（volumes）整页缺席（dry/Lazydocker/1Panel/群晖均有卷列表）。
6. **可靠性是专精工具的共同底座**：Dozzle 的「不存储、纯实时」与有界内存、Lazydocker 的「重启后日志自动重连」（用户的原始抱怨）、我们的暂停不丢行 backlog 是同族设计；反例是 Dockge 作者自述动机——Portainer 部署 stack 时转圈数分钟且报错含糊。**错误呈现与重连是被竞品作者们反复用脚投票的一等公民**，值得单独成批。
7. **国产 NAS 生态（群晖/宝塔/1Panel 等）的高度趋同**：镜像加速源 + 代理设置、compose 项目（NAS 叫「项目/编排」）、映像检查更新 + 提醒、编排备份/还原。这是用户重度场景的刚需四件套，我们已有 2.5 件（检查更新有、compose 有雏形、加速源只读、备份/还原无）。
8. **移动端/窄屏**：所有桌面型竞品（Portainer/Docker Desktop/Podman Desktop）都不为手机优化，NAS 系（群晖等）靠响应式网页凑合。我们当前的地板是「容器表格自带 760px 最小宽、在列表自己的 scroller 内横滚」（ContainerListView.vue:608；整列 850px 地板已在 `caa9f8e` 有意撤除，工具栏必须按可见宽度排版），与 Docker Desktop 的「可自定义列」思路可以合成一个低成本批次（列裁剪 + 窄列降级），不必专门做移动端应用。

## 二、逐家调研

### 2.1 Portainer CE / BE ——「更新状态上列表」与「Rebuild」的范式

- 定位：CE 免费轻量管理 UI（Docker/Swarm/Podman/K8s/ACI），BE 叠加 RBAC、GitOps、边缘管理、审计、SSO（[README](https://github.com/portainer/portainer)）。CE 明确「非生产自担」，BE 是商业层。
- 信息架构：容器/镜像/网络/卷/Stacks/注册表/设置（docs 用户手册分节）；容器列表搜索框旁一枚「全量重检」按钮（[containers 文档](https://docs.portainer.io/user/docker/containers)）。
- **精华 1：镜像更新指示列**——「Images up to date」列三态：绿勾=最新 / 橙叉=远端有新版 / 灰杠=无法判定；逐行可单查、全列表可一键重检。把「该不该升级」做成列表第一眼事实。
- **精华 2：Duplicate/Edit + Rebuild**——编辑或复制容器时按原参数重开表单；从 stack/模板部署的容器出现 Rebuild 按钮，按原始定义带着新镜像重部署（[edit 文档](https://docs.portainer.io/user/docker/containers/edit)）。这正是我们 clone 预填 + 5 步更新流差的那一跳。
- **精华 3：Webhook 自动重部署**——容器/Stack 挂 webhook URL，注册表 push 新镜像后 POST 即重建容器并拉最新镜像（[webhooks 文档](https://docs.portainer.io/user/docker/stacks/webhooks)）；社区用它接 Home Assistant/Node-RED 做手动按钮升级。
- 其余：容器日志/统计/控制台/所有权（BE 语义）；App Templates 模板商店；BE 的边缘代理与 GitOps 属企业层。
- 我们的态度：抄「更新指示列 + 一键全量重检 + Rebuild 语义」；webhook 机制需要服务端常驻，桌面形态缓行；RBAC/审计不抄（单用户）。

### 2.2 Docker Desktop ——批量、Compose 分组与日志搜索的完成度标杆

- 定位：官方桌面套件，Dashboard 集中管理容器/镜像/卷/构建/K8s，header 有快搜（[use-desktop 文档](https://docs.docker.com/desktop/use-desktop/)）。
- **精华 1：多选批量操作**——行复选框多选后批量 start/pause/stop/delete（[Containers 视图文档](https://docs.docker.com/desktop/use-desktop/container)）。
- **精华 2：Compose 项目一等公民**——Compose 应用在网格里分组折叠，项目复选框全选其容器，项目级 start/stop/pause/restart/delete + 项目详情。
- **精华 3：日志查看器**——Ctrl+F 搜索高亮、Enter/Shift+Enter 跳转、正则或精确匹配、时间戳开关、一键复制全部、多容器应用里按容器过滤日志、日志内链接可点。
- **精华 4：Stats 选项卡与自定义列**——CPU/内存/网络/**磁盘读写**随时间展示；网格列（CPU%、内存用量/上限、磁盘 IO、PIDs、最近启动）可自定义并跨会话记忆。
- 其余：Inspect 选项卡含 SHA-256/端口映射/本地路径；复制 `docker run` 命令；Docker Debug（对无 shell 的 distroless 容器塞工具箱）；端口浏览器打开；Gordon AI 诊断（不同赛道不抄）。
- 我们的态度：批量、Compose 分组、日志搜索三件全抄；自定义列与列记忆并入窄屏批次；Docker Debug 的精神（对无 shell 容器的兜底终端）记为远期。

### 2.3 Lazydocker ——TUI 的信息密度与「重启即重连」

- 定位：Go + gocui 的终端 UI，docker 与 docker-compose 同窗（[README](https://github.com/jesseduffield/lazydocker)）。作者的开场白是痛点自白：跨多个终端窗口追踪容器几乎不可能，一切应一键可达。
- 精华：状态一览 + 日志 + ASCII 指标图（图形可自定义度量）一屏三栏；attach/重启/删除/**重建**容器与服务；查看镜像的祖先层（image history 可视化）；**prune 容器/镜像/卷**一键回收磁盘；服务挂掉后日志流自动重连（作者的原始抱怨：`logs --follow` 随服务死掉，重启后得手动重跑）。
- 我们的态度：prune 全家桶与「重启后日志流重连」直接对应我们的可靠性批次；ASCII 图我们已有 SVG sparkline，无需跟进。

### 2.4 Dockge ——compose.yaml 为中心的反应式编辑流

- 定位：Uptime Kuma 作者的「fancy, easy-to-use and reactive」compose 栈管理器（[README](https://github.com/louislam/dockge)）。作者动机：Portainer 部署 stack 时转圈几分钟、报错不清楚。
- 精华：compose.yaml 创建/编辑/启停/重启/删除 + **更新镜像**按钮；交互式 YAML 编辑器 + 交互式 Web 终端 + 拉取/up/down 进度实时回显（反应式）；**`docker run ...` 命令一键转 compose.yaml**；1.4.0 多 agent（一套界面管多台 Docker 主机）；**文件不绑架**——栈文件就在磁盘上，随时可以用原生 `docker compose` 命令操作。
- 我们的态度：YAML 编辑器（我们有只读的 writeYaml 路径，缺编辑与实时输出）、`docker run`→compose 转换（低频但传播力强）、文件不绑架原则（我们 compose.ts 的路径纪律已同此精神）均值得吸收；多 agent 与我们「一连接=一主机」的 SSH 模型天然不同构，不抄。

### 2.5 Yacht ——模板化的正反两面教材

- 定位：容器管理 UI，主打模板与 1-click 部署（[README](https://github.com/SelfhostedPro/Yacht)）。README 顶部自述「很久没更新」，仅做过安全修复，后端正在 TypeScript 重写（迁移未完成）。
- 精华：模板框架兼容 Portainer 模板 URL，模板内 `!var` 变量映射到服务器级默认值（如 `!config` → 统一数据根目录）；集中式卷管理设置；compose 兼容；模板一键更新。
- 我们的态度：**模板机制本身可抄**（模板=预填的创建向导 JSON，与某国产 NAS 的「常用配置模板」同构），但以 Yacht 的停滞为戒——模板功能要挂在创建向导上而非另立门户。

### 2.6 Podman Desktop ——多引擎与托盘的桌面形态参照

- 定位：容器与 K8s 的图形开发环境，安装/配置/更新 Podman 本体（[README](https://github.com/podman-desktop/podman-desktop)）。
- 精华：仪表盘管容器/镜像/pod/卷；**多引擎并存**（Podman/Docker/Lima/crc）一键切换；系统托盘查状态不丢焦点；OCI 注册表管理与代理设置的企业能力；扩展生态（Docker/ps1/kube 等扩展）；pod 与 K8s 互转。
- 我们的态度：我们引擎层已支持 docker/podman/nerdctl/wslc 四运行时（commands.rs 差异收口），「多引擎并存切换」在 UI 层是会话属性而非窗口结构，暂不需要；托盘与扩展生态不同形态不抄。

### 2.7 Rancher / Fleet ——多集群与 GitOps 的重量级参照（不抄）

- 定位：Rancher「Complete container management platform」面向多集群 K8s（[repo](https://github.com/rancher/rancher)）；Fleet 把 Git 仓库下发到大规模 K8s 集群（[fleet](https://github.com/rancher/fleet)）。
- 值得看的是思想：资源在 Git 里、集群向 Git 收敛；权限按 cluster/project 分层下发。
- 我们的态度：单机/单连接桌面场景不引入集群抽象与 GitOps 控制器。与 Fleet 思想最近的可落点只是「compose 文件入库 + 手动应用」，列为不抄。

### 2.8 Komodo ——多服务器自动化的告警与同步

- 定位：跨多服务器构建部署软件的自动化平台，服务器数无上限（[官网](https://komo.do)、[readme](https://github.com/moghtech/komodo)）。
- 精华：服务器 CPU/内存/磁盘监控 + **阈值告警**；浏览器内**持久化具名 shell 会话**（服务器与容器）；Stacks（compose 文件部署单元）跨服务器部署；git 仓库自动构建镜像推送注册表；**声明式 Resource Sync**（资源定义在 git 的 TOML 里，向服务器收敛）；Webhook 触发；RBAC 用户组按资源分级；API/CLI/类型安全客户端全家桶。
- 我们的态度：阈值告警与「异常容器提醒」值得我们通知中心承接；持久具名终端会话与我们的终端 tab 模型同构，可吸收其命名/复连语义；其余多服务器编排不抄。

### 2.9 Shipwright ——经核实排除

- 定位核实：shipwright-io/build，「a framework for building container images on Kubernetes」（[repo](https://github.com/shipwright-io/build)），830 stars 活跃。它是 K8s CRD 驱动的镜像构建框架（Cloud Native Buildpacks/Buildah/Kaniko 等策略），**不提供 Docker 容器管理 UI**，与本调研同类项不重合，排除出对标清单。

### 2.10 Dozzle ——日志专精的深度标杆

- 定位：轻量实时容器日志查看器，不存储日志（[README](https://github.com/amir20/dozzle)、[dozzle.dev](https://dozzle.dev)）。
- 精华：容器名**模糊搜索**；日志**正则搜索**与 **SQL 查询**（内置 SQL 引擎查日志行）；**分屏同时看多容器日志**；实时 CPU/内存统计条；多用户认证与反向代理授权；Swarm 模式；**Agent 模式聚合多 Docker 主机**；每容器按镜像名配应用图标（取自 homarr-labs/dashboard-icons）；7MB 级内存足迹；姊妹项目 dtop 做 top 式监控并与 Dozzle 互跳。
- 我们的态度：正则搜索我们有「仅错误」启发式过滤，该升级为真正的搜索（高亮+跳转）；应用图标性价比极高，值得抄；SQL 查日志过重，缓行；分屏多日志在我们抽屉模型里等价于「多容器日志合并流（docker compose logs 语义）」，先做合并流。

### 2.11 ctop ——指标网格（已停滞，仅供形态参考）

- 定位：top 式容器指标界面，多容器实时网格 + 单容器视图，支持 Docker/runC（[README](https://github.com/bcicen/ctop)）。17.9k stars 但 2024-07 后无提交。
- 精华：以「列=指标、行=容器」的实时网格把「谁在吃资源」变成第一眼可见。
- 我们的态度：我们的容器列表无任何资源列；把 stats 采样以节流方式补进列表（或进入详情 stats 选项卡）是其精神，注意我们「没人看就不采样」纪律的边界——列表可见且窗口在前时才采样。

### 2.12 dry ——事件流、磁盘占用与卷列表的终端实现

- 定位：终端 Docker 管理器，近期正在重构 workspace 模式（[README](https://github.com/moncho/dry)）。
- 精华：全局键位 F8 **Docker 磁盘占用**（`docker system df` 的表格化）、F9 **最近 10 条 docker events**、F7 daemon 信息、`1-8` 号键在容器/镜像/网络/**卷**/节点/服务/栈/compose 项目间切换；`:` 命令面板；过滤/排序；Quick Peek 侧栏；窄终端降级单栏。
- 我们的态度：`docker system df` 一页清 + 事件流查看 + 卷列表页是三个直接可抄项；命令面板与我们终端已有的命令面板体系可共用骨架。

### 2.13 Gui-for-docker ——不可查证

- 任务点名核实：GitHub API（仓库直查、搜索 `Gui-for-docker in:name`、用户 finanium 仓库列表）与站内检索均未找到该项目；相近命中的是 jlesage/docker-baseimage-gui（Docker 基础镜像，非管理器）与已归档的 docker-archive-public/docker.kitematic。**结论：无法取证，不纳入对标**。若用户另有所指（如某具体仓库已改名/删除），待补充线索后再调研。

### 2.14 1Panel ——容器「升级/清理/模板/加速源」四件套的国产面板标杆

- 定位：现代开源 Linux 服务器运维面板，容器管理为核心模块（[README](https://github.com/1Panel-dev/1Panel)）。IA 从源码树直接取证（frontend/src/views/container/，dev-v2 分支）。
- 源码树可见的完整能力面：**dashboard**（容器概览）+ docker-status；容器列表 + **operate**（编辑容器，含 network/volume 选项卡）+ **upgrade（容器升级）** + commit + **file-browser（容器文件浏览器）** + inspect + **monitor** + rename + terminal + **prune（容器清理）**；镜像 pull/push/load/save/tag/build/**remote**/prune/delete；网络 create/detail；**卷 volume create/list**；**编排 compose** + **模板 template（import/detail）**；**镜像仓库 repo 管理**；**setting：mirror（镜像加速）/registry/ipv6/log（日志轮转）/sock-path**。
- 精华：①「升级」独立成功能（不是裸 pull）；②容器级与镜像级各自 prune；③编排模板库（导入/详情/复用）；④加速源是**可写设置**；⑤容器文件浏览器是一等入口。
- 我们的态度：四件套全抄（upgrade 我们半有、prune 只剩镜像、模板与加速源写入是新增）；文件浏览器我们已有（openFiles 进文件工作台），保持。

### 2.15 宝塔面板 Docker 模块 ——编排备份/还原是独有亮点

- 定位：面板内 Docker 可视化模块（闭源），容器创建（镜像/Compose 模板两种来源）、容器编排、实时监控（[官方手册帖](https://www.bt.cn/bbs/thread-95674-1-1.html)）。
- 精华：**容器编排的备份与还原**（编排页面支持「从备份创建」，上传备份文件还原编排）；把任意 `docker run` 命令接管为面板内可编辑容器的引导流程（[教程贴](https://www.bt.cn/bbs/thread-95674-1-1.html) 同源）。
- 我们的态度：编排备份/还原（导出 compose 文件 + 参数快照）映射到我们已有的文件工作台可低成本实现；`docker run` 接管与 Dockge 的转换器同构，合并为一个条目。

### 2.16 群晖 DSM Container Manager ——「映像检查更新提醒」的 NAS 范式

- 定位：DSM 7.2 的 Docker 套件，五页签：容器/映像/注册表/网络/项目（原生 compose）。取证：KB 为 JS 渲染页，抓不全，以下为 KB 检索摘要与[更新方法实证文](https://juejin.cn/post/7327353593890193459)交叉转述，可信度中等。
- 精华：映像页内置**检查更新**并在有新版时**提醒**（提醒进 DSM 通知中心）；一键更新=停旧容器→用新映像重建；注册表设置里配**镜像加速源**；项目（compose）部署与重建；容器导出。
- 我们的态度：与某国产 NAS 同族的四件套（加速源/项目/检查更新提醒/导出）已在本报告多条出现；「更新提醒进通知中心」对应我们桌面通知中心的既有入口，列入镜像批次。

### 2.17 某国产 NAS 的 Docker 子应用 ——本仓已有内部拆解，此处只列裁定

- 全量证据见内部拆解记录（原报告已归档移除：导航六项/9 态/创建向导分区卡/更新 5 步确认/错误码 27 条映射）。本报告补充三条裁定：
- 精华 1：**镜像仓库页 = 加速源（拖拽排序优先级）+ 代理表单**（G5），是「注册表设置」的完整形态。
- 精华 2：**更新流的防呆链**：「有新版本」徽标 → 5 步确认（先停容器/数据可能丢失/加速源注意/不可暂停取消/失败可手动）→「请关闭以下容器再更新」列表 → 升级中防重复（0x03200011/12）。我们的 ImageUpdateDialog 已复刻 5 步确认，缺后面的「重建」终点与防重复引擎位。
- 精华 3：**Compose 运行中配置只读** + 常驻「编辑需重新构建才生效」提示（G6）——受控应用（受控 apply）的 NAS 表达。

### 2.18 Watchtower（及续作）——自动更新的策略清单

- 原版 containrrr/watchtower 已停止维护（README 顶部声明 + [讨论 #2135](https://github.com/containrrr/watchtower/discussions/2135)）；活跃续作 [nicholas-fedor/watchtower](https://github.com/nicholas-fedor/watchtower)（4.9k stars）。
- 策略精华：按 cron 间隔拉新镜像 → **优雅停止** → **用部署时的原参数重建** → 可选 `--cleanup` 删旧镜像；支持只监控不更新、按容器排除、生命周期钩子（更新前后回调）。
- 我们的态度：不做守护进程；把「原参数重建」做成容器级手动动作（2.1/2.14 的 Rebuild/upgrade 同一条），后续再考虑「计划任务」档位接我们的通知中心。
