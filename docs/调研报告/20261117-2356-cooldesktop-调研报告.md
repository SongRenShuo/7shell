# cooldesktop 调研报告

> 调研对象：houxinlin/cooldesktop（F:\code\Java\Github\other\houxinlin\cooldesktop，本地只读检出，未跑构建）
> 调研目的：为 7shell「Linux 桌面」连接类型提供参考——7shell 要的是通过 SSH 连接/隧道承载、在客户端渲染远程 Linux 主机真实桌面的可视化页面。
> 调研方法：先读 README / install.sh / cool_sum.txt / 根级构建文件建立全局认知，再按模块深挖源码主线。所有结论带 `文件:行号` 出处（相对 cooldesktop 根目录）。文中标注「推断」处为证据不足、经分析得出的判断。

## 结论速览

1. cooldesktop 不是远程桌面，而是「Web 桌面壳」：在浏览器里画一个仿操作系统的窗口管理器，把文件管理、终端、日志追踪等服务器管理功能做成可开多窗口的 Web 应用，目标是「像操作本地系统一样操作远程 Linux」（README.md:3-31）。
2. 全仓没有任何真实桌面采集痕迹：grep 不到 X11/Xvfb/Wayland/VNC/xrdp/截屏/java.awt.Robot 任何一处，「桌面」与「远程主机画面」无关。
3. 部署模型是重型的：目标 Linux 服务器上常驻一个 Spring Boot fat jar（要求 JDK 11+，install.sh 用 root 权限注册 systemd 服务），浏览器直接访问服务端 2556 端口，与 SSH 隧道无关。
4. desktop-loader 是第三方应用热加载器：按魔数区分 jar 应用与自定义 .webapp 包，用独立类加载器把 @Component 类注册进运行中的 Spring 容器、动态注册带应用 id 前缀的 Controller，支持卸载——这是全项目最有个性的部件。
5. 传输层是双通道：STOMP over SockJS（广播主题 /desktop-topic/event，服务端推送 12 类事件）+ 终端专用原生 WebSocket（文本帧，ANSI 转义直通，前端 xterm.js 渲染）；消息体是 JSON map（subject + action + 任意键值）。
6. 输入注入不存在：没有任何鼠标键盘事件注入到桌面层的机制；「输入」只有两条路——终端键盘输入写 PTY stdin，其余操作全是标准 HTTP API。
7. 终端链路用 pty4j 在服务端本地起 /bin/bash，不是 SSH 会话；窗口大小同步协议是「setSize + 四个定长 4 位数字」的字符串（LinuxTerminal.kt:45-52），比较粗糙。
8. 认证靠魔改版 tomcat-embed-core（内含 TomcatGlobalAuthenticationValve 全局认证阀 + 登录 Servlet + IP 限流），源码不在本仓，密码明文存 ~/cooldesktop-work/password.conf；WebSocket 层本身零鉴权（握手发随机 UUID 当 Principal）。
9. desktop-file 的分片上传协议（预检目标 → 分片落盘 → 按字节总和判完整 → 锁内合并 → WebSocket 通知刷新）与异步压缩/粘贴的「提交任务即返回 + WS 推结果」模式值得借鉴。
10. 前端是 Vue SPA，源码在独立仓库 cooldesktop-web（README.md:88），本仓只有构建产物；从产物里可确认 xterm.js、拖拽窗口、iframe 内嵌 Web 应用三种技术。
11. 单用户模型：无多用户、无权限分级、服务端剪贴板是全局单例，root 进程直接读写全盘——定位是个人服务器管理工具，不是多人协作产品。
12. 对 7shell 的核心结论：它的「桌面」形态与 7shell 要的真实桌面渲染不匹配，但其 STOMP 主题协议设计、任务异步化 + WS 推送 UX、文件管理器交互、第三方应用加载器思路可以借鉴；SSH 承载与零服务端部署这两条 7shell 底线它都不满足。

## 1. 项目定位与整体架构

### 1.1 它是什么、给谁用

README 开篇一句话定位：「CoolDesktop 是一个 Linux 服务器管理软件，采用全新的操作方式，让您像操作本地系统一样，操作远程 Linux」（README.md:3）。功能清单（README.md:5-31）：仿操作系统的多窗口 + 第三方软件加载卸载、文件复制粘贴剪切压缩解压、多终端、文件上传拖放、日志追踪、jar 一键启停、文件分享链接、开发自定义管理软件；软件商店提供图片查看器、文件编辑器、系统监视器、Java 进程管理器（可热替换、GC、在线反编译内存中的 class）。

所以它的用户画像是「个人 Linux 服务器（尤其是 Java 应用服务器）的运维者」，形态是把 Web 版服务器管理面板做成操作系统的样子。它面向的是一台自己有 root 权限的服务器，而不是企业级多人托管场景。

### 1.2 部署形态

install.sh 展示了官方部署路径：root 身份运行，创建 /opt/cooldesktop 目录，从 cool_sum.txt 里取 jar 的 sha1 与下载地址做循环下载校验（install.sh:20-36），生成 systemd 服务文件，`User=root`、`ExecStart=<java> -jar cooldesktop.jar`（install.sh:39-53）。cool_sum.txt 就是一行「sha1 + URL」（cool_sum.txt:1）。README 说明默认端口 2556，浏览器直接访问（README.md:68），首次登录默认密码 `cooldesktop`（README.md:75-80）。

desktop-startup 模块的 Startup.java 是另一个启动入口：定位自身目录下的 `/cooldesktop/CoolDesktop.jar`，JDK 版本低于 11 时改用随包分发的 `/jre`，然后 ProcessBuilder 起子进程并把输出重定向到日志文件（Startup.java:36-49）。配套的 desktop-web/build.gradle.kts 里有一个 `install` 任务，用 jlink 裁剪出精简 JRE 到 bin/jre（desktop-web/build.gradle.kts:20-36），即官方发布物是「启动器 + fat jar + 精简 JRE」三件套。

一个值得注意的约束：Application.kt 的 main 里检查 `os.name`，非 Linux 直接 error 退出（Application.kt:33-41）——它是纯服务端 Linux 程序，Windows 只能用于开发调试。

### 1.3 模块职责与协同

settings.gradle.kts 声明 8 个模块（settings.gradle.kts:1-9）。协同关系很直接：desktop-web 是唯一产出 fat jar 的聚合模块，依赖 desktop-file / desktop-loader / desktop-database / desktop-websocket / desktop-system 五个业务模块（desktop-web/build.gradle.kts:5-9），而所有模块都依赖 desktop-common（根 build.gradle.kts:96-97）。desktop-startup 只是启动器，不进 Spring 世界。

各模块职责按源码归纳：

- desktop-common：常量、Directory（工作目录布局）、日志抽象、通用模型（FileHandlerResult/Page/HttpResponseBody）与 Kotlin 扩展。没有业务。
- desktop-database：H2 文件库 + JdbcTemplate 薄封装，4 张表（sys_config / app_properties / sys_log / share_file_map，CooldesktopDatabaseTablInitialization.kt:18-27），庘认证都没配（CoolDesktopDatabaseConfig.kt:20）。
- desktop-file：文件域全部能力（浏览、上传下载、压缩解压、文本编辑、图标缩略图、分享链接、jar 启停、tail 入口），服务接口 IFileService.kt:12-68 一个接口全覆盖。
- desktop-loader：第三方应用热加载（见第 2 节），依赖 desktop-file 的目录扩展与 desktop-system 的资源注册。
- desktop-system：系统能力中枢——终端（pty4j）、tail、命令模板、通知与审计 AOP、壁纸、SSH 密钥管理、Spring 动态注册器（bean / RequestMapping / 静态资源）、分享下载 Servlet。
- desktop-websocket：STOMP 事件通道 + 终端原生 WebSocket 的接线层，业务不多，主要是两个 Configurer 和两个 Action。
- desktop-web：Spring Boot 主应用，控制器薄层（应用管理 API / 文件 API / 系统 API / 应用静态资源），聚合打包。

### 1.4 两个非常规的构建决策

根 build.gradle.kts 有两处决策影响了对这个项目的理解，值得单独说。

第一，它排除了官方 spring-boot 与 spring-webmvc 依赖，改用作者自编译的 jar（build.gradle.kts:77-81 排除，:105/:108 引入 desktop-lib 下的 spring-boot-2.6.1.jar 与 spring-webmvc-5.3.20-SNAPSHOT.jar），注释说明是为了配合魔改。这属于深度魔改框架的路径，构建强依赖作者本机路径（build.gradle.kts:38-51 的 copyLib 任务从 `/home/HouXinLin/projects/java/...` 拷 jar），换环境不可复现。

第二，`compileOnly("org.apache.tomcat.embed:tomcat-embed-core:9.0.58")` + `runtimeOnly(files("desktop-lib/tomcat-embed-core.jar"))`（build.gradle.kts:101-102），注释明说「tomcat 为二次开发的 jar，主要功能全局拦截，进行登录」。desktop-lib/tomcat-embed-core.jar 里确实有 TomcatGlobalAuthenticationValve、TomcatGlobalAuthenticationHttpServlet（含 IPLimitTask 内部类）、TomcatShareFileHttpServlet 等自研类（unzip -l 实测类清单），源码不在本仓。认证（第 6 节）整个建立在这个闭源 jar 上。

## 2. 桌面/画面从哪来：没有真实桌面，只有 Web 桌面壳

这是本次调研最重要的一条定性结论：**cooldesktop 与真实桌面采集无关**。

取证方式是反向验证：对全仓 .kt/.java/.kts/.properties 用 `xvfb|x11|xdotool|xauth|vnc|xrdp|wayland|java.awt.Robot|screenshot|Xvnc` 大小写不敏感搜索，命中数为 0。后端没有任何截屏、帧采集、显示服务器交互的代码。所谓「桌面」是浏览器里的一个 Vue 单页应用：壁纸、图标、任务栏、可拖拽多窗口都是 DOM，壁纸是用户上传后存在服务器的图片文件（CoolDesktopSystem.kt:66-79 changeWallpaper 上传到 ~/cooldesktop-work/config/wallpaper 并写库），经 /system/resource/wallpaper/** 静态映射返回（SystemResourceMvcConfigurer.kt:12-18）。桌面上的「文件快捷方式」只是把一组路径存进 H2 的 app_properties 表（CoolDesktopSystemController.kt:115-144），图标由服务端按文件类型返回 PNG（FileServiceImpl.kt:252-259，icon 资源就躺在 desktop-file/src/main/resources/static/icon/ 下）。

因此它回答 7shell 的问题很明确：**「远程 Linux 主机的真实桌面画面」在这个项目里根本不存在，不存在可供借鉴的画面采集/编码/传输流水线。**

### 2.1 desktop-loader 是干什么的

desktop-loader 不是画面加载器，而是「第三方应用热加载器」——README 第 0 条「拥有加载、卸载第三方软件能力」的实现。应用分两类（ApplicationManager.kt:23-27）：

- **EASY_APP（jar 应用）**：一个普通 jar，内含 app.properties 描述文件（EasyApplicationLoader.kt:76）与若干 @Component 类。加载时用魔数识别（ApplicationTypeDetection.kt:14-16，`PK\x03\x04` 即 ZIP/JAR 魔数），读 app.properties 校验必填项与最低系统版本（EasyApplicationLoader.kt:163-179, 205-213），创建支持「jar 套 jar」的类加载器——复用 Spring Boot loader 的 JarFile/嵌套 URL（EasyApplicationLoader.kt:215-229，ApplicationClassLoader 直接继承 LaunchedURLClassLoader，ApplicationClassLoader.kt:6-8）——然后扫描 @Component 类注册进运行中的 Spring 容器（EasyApplicationLoader.kt:234-265），CoolDesktopBeanRegister 用 defaultListableBeanFactory.registerBeanDefinition 动态注册/销毁（CoolDesktopBeanRegister.kt:30-67），并做了一个类加载器身份校验防两个应用同包名互踩（CoolDesktopBeanRegister.kt:54-58）。Controller 注册由自定义 RequestMappingRegister 完成，它会自动给应用的每个 mapping 加 `/{applicationId}` 前缀并支持动态反注册（RequestMappingRegister.kt:54-68）。卸载时依次调用应用的可选 uninstall 方法、销毁 bean、反注册 Controller、删 jar 文件（EasyApplicationLoader.kt:141-157）。
- **WEB_MINI_APP（web 应用）**：自定义二进制格式 `.webapp`：4 字节魔数（0x007913E）+ 4 字节 JSON 头长度 + JSON 应用描述 + 静态资源包（FilePackage 表，WebMiniApplicationLoader.kt:40-52），staticResOffset 指向资源区。运行时按路径查资源表、带内存缓存返回（WebMiniApplicationWrapper.kt:14-22），HTTP 入口是 `/desktop/webapplication/{applicationId}/**`（WebApplicationResourceController.kt:35-49），用 Tika 探测 Content-Type。本质上是「前端页面打包成单文件、后端代管静态资源」的最小 Web 应用。
- **AloneApplicationLoader**：一个空壳，注释「预留」（AloneApplicationLoader.kt:7-16），推断是给独立进程/独立 Tomcat 应用预留的扩展点，未实现。

安装分发走 ApplicationInstallDispatcher：按字节魔数选 loader（ApplicationInstallDispatcher.kt:52-59）；在线安装走 ApplicationDownloadManager 的单线程安装队列 + InstallStep 流水线（下载 → 安装 → 通知客户端刷新），每步进度经 STOMP 推到浏览器（ApplicationDownloadManager.kt:63-74, 105-115）。软件商店服务端地址存在 H2 配置里，默认 cool.properties 写死 http://www.houxinlin.com:8081（cool.properties:1）。

应用与主程序的交互面是 desktop-lib 里另一个闭源 jar desktop-application-definition-1.0-SNAPSHOT.jar（Application/EasyApplication/WebMiniApplication/ApplicationLoader 接口定义，unzip 类清单实测）+ cooldesktop-application-event-definition jar（ApplicationInteractive/ApplicationMessagePublish 生命周期与消息接口，EasyApplicationLoader.kt:8-11 import）。客户端打开/关闭应用的事件从 STOMP 进来（CooldesktopMessage.kt:16-20），转发给 jar 应用的 onOpen/onClose（ApplicationManager.kt:45-60）。

## 3. 传输与渲染

### 3.1 双 WebSocket 通道

**STOMP over SockJS（事件与通知）**：端点 /desktop-socket-endpoint，simple broker 前缀 /desktop-topic，客户端发送前缀 /desktop（DesktopWebSocketConfigurer.kt:19-23）。广播主题枚举集中在 Constant.WebSocketSubjectNameConstant，共 12 个：文件夹刷新、安装进度、文件事件、终端消息、壁纸刷新、应用刷新、打开目录、压缩结果、成功/错误通知、应用消息推送、shell 执行结果、分享链接刷新（Constant.kt:43-57）。消息体是 JSON map：`{subject, action, ...任意键值}`（WebSocketMessageBuilder.kt:7-28）。客户端到服务端只有一个 @MessageMapping("/event")，用于开/关应用（CooldesktopMessage.kt:16-20）。订阅/断开事件由 WebSocketEventListener 按 destination 分发给 IStompSubjectAction 实现（WebSocketEventListener.kt:27-57）。

服务端推送统一收敛在 CoolDesktopEventAction.send：无人订阅时进离线队列（上限 5 条，满了直接丢弃）、有订阅者时 convertAndSend 到 /desktop-topic/event；另有一条 DelayQueue 线程做延迟发送；最后一个客户端断开时 TailManager.stopAll() 清理所有日志追踪（CoolDesktopEventAction.kt:32-77）。

**终端专用原生 WebSocket（非 STOMP）**：/ws/websocket/terminal，TextWebSocketHandler，连接建立即创建终端、断开即销毁、消息原文写入 PTY（XterminalWebSocketConfigurer.kt:20-34）。注意它 setAllowedOrigins("*")（XterminalWebSocketConfigurer.kt:34），且用 TextMessage 而非 BinaryMessage 回传（SshMessageListener.kt:8-12）——终端输出（含 ANSI 转义序列）以 UTF-8 文本帧直通前端，前端 xterm.js 渲染。没有压缩、没有帧率控制——文本终端天然不需要。

### 3.2 异步任务与推送的通用模式

长耗时文件操作（粘贴、压缩、解压）的接口设计是「提交即返回 taskId，结果用 WebSocket 推」：FileServiceImpl 的这些方法都挂在 @NotifyWebSocket 注解下，AOP 在方法返回/抛异常后自动把结果转成 JSON 推给客户端（CoolDesktopNotifyWebSocketAspect.kt:39-68，注解用法见 FileServiceImpl.kt:78, 280, 302）。前端拿到 taskId 与主题后做进度刷新。这个模式在这个项目里被反复使用，是最成熟的工程习惯。

### 3.3 前端在哪里、怎么渲染

前端源码在独立仓库 houxinlin/cooldesktop-web（README.md:88-94，`npm run build` 后把 dist 拷进 desktop-web/src/main/resources/static/），本仓只有构建产物：index.html 引 sockjs.js 与两个 ES module bundle（static/index.html）。对产物 bundle 做关键词计数（index.60a4d698.js，634KB）：xterm×58、drag×24、Stomp×10、iframe×8、SockJS×1。可以确认前端三件套：xterm.js 渲染终端、Vue 拖拽窗口管理器、Web 类应用用 iframe 内嵌（推断：iframe 标签出现于应用窗口宿主，配合 /desktop/webapplication/ 资源服务）。没有 canvas 绘图、没有视频流、没有像素级渲染——再次印证它是 DOM 桌面。

## 4. 输入与交互

### 4.1 不存在输入注入

与画面采集的结论一致：cooldesktop 没有任何把鼠标键盘事件注入到 Linux 图形层的机制。xdotool/XTest/java.awt.Robot 在仓库里出现次数为零。「输入」只有两条通路：

1. 终端键盘输入：前端 xterm.js 捕获按键 → WebSocket 文本帧 → TerminalSocketAction.onMessage → writeCommand 入队（TerminalSocketAction.kt:30-34）→ 消费线程写 PTY stdin（LinuxTerminal.kt:79-95）。
2. Web 应用交互：全部是常规 HTTP API（文件操作、系统配置等），每个按钮背后是一个 REST 端点，不存在「模拟桌面事件」。

### 4.2 终端尺寸同步协议

前端窗口变化时通过两条约定消息同步（LinuxTerminal.kt:55-63, 84-86）：`INIT_HOME_TERMINAL:<home>` 设定初始目录并放行 PTY 创建（waitInit CountDownLatch，LinuxTerminal.kt:25, 56-59, 66）；`setSize` 前缀消息携带 col/row/w/h 四个定长 4 位数字段，服务端按固定下标切割解析后设 WinSize（LinuxTerminal.kt:45-52）。这套协议能用但很脆：列数超过 9999、或某个数字段不足 4 位都会解析错乱；用魔数前缀字符串而不是结构化消息，属于这个项目里比较粗糙的部分。

### 4.3 窗口管理

多窗口、最大化/最小化、拖拽全部在前端 Vue 里实现（产物 bundle 的 drag 关键词与 README.md:5 的功能声明），后端不参与窗口状态管理，推断窗口布局不持久化。后端参与的只有两类「窗口级」数据：桌面快捷方式列表（存 H2，CoolDesktopSystemController.kt:115-144）和每个应用窗口对应的 API 前缀/资源前缀隔离（/{applicationId}/）。文件拖放上传是前端分片调 chunk/upload（README.md:13「上传文件托放既可完成」+ StaticResourceController.kt:186-190）。

### 4.4 服务端文件剪贴板

「复制/剪切/粘贴」是服务端单条目全局单例：ClipboardManager 只记一个 memoryFilePath + 一个 actionCommand（copy/cut/none）（ClipboardManager.kt:10-15），粘贴时 copyRecursively 或 copy 后删源（ClipboardManager.kt:50-74）。没有任何用户/会话维度隔离，两个浏览器标签页会互相覆盖剪贴板。

## 5. 周边能力

### 5.1 desktop-file：文件域全家桶

IFileService.kt:12-68 一个接口定义了全部 22 个操作，REST 入口在 StaticResourceController（/desktop/api/file/**，StaticResourceController.kt:23-332）。几处有设计含量的实现：

- **目录列表并发构建**：listDirector 对目录下每个条目提交线程池任务，CountDownLatch 整体等待 1 分钟上限，文件夹排前、文件排后（FileServiceImpl.kt:173-212）。HTTP 层面一个请求拿全量属性（FileAttribute 含大小/权限/类型），前端不用逐个请求。
- **分片上传**：chunkUpload 预检目标存在性与读写权限 → 分片按 blobId 落盘到 fileupload/chunk/{chunkId}/ → 用「已落盘分片字节总和 == total」判断是否传完 → fileMergeLockMap + synchronized 保证只有一个线程合并 → 合并后删分片目录并经 WS 推 refresh 事件让前端刷新目录（FileServiceImpl.kt:129-168）。配套 fileMerge 独立接口（FileServiceImpl.kt:101-127）。单请求上限 25MB（application.properties:1-3）。
- **压缩/解压**：zip/tar/7z 三种，实现在 compress 包（ZipCompress/TarCompress/SEVENZCompress， commons-compress + tukaani xz，根 build.gradle.kts:113-114），异步执行 + @NotifyWebSocket 推结果（FileServiceImpl.kt:280-319）。
- **文本编辑**：getTextFileContent/setTextFileContent 直接读写（FileServiceImpl.kt:331-351），支撑「文件编辑器」应用。
- **图标与缩略图**：Tika 探测类型（根 build.gradle.kts:125 引 tika-core），内置 40+ 个扩展名 PNG 图标，图片缩略图用 thumbnailator（FileServiceImpl.kt:217-259）。
- **jar 一键启停**：runJarFile 先用 Attach API（com.sun.tools.attach.VirtualMachine，JarUtils.kt:6, 12-40）列 Java 进程、按 jar 路径过滤 pid，再 nohup java -jar 后台启动、轮询确认启动成功；stopJar 遇到同路径多进程会拒绝执行（FileServiceImpl.kt:364-386）。依赖 desktop-lib/tools.jar（根 build.gradle.kts:104），这是 JDK8 时代的 tools.jar 路径假设，运行端 JDK11+ 实际靠 jdk.attach 模块（jlink 打包用了 ALL-MODULE-PATH，desktop-web/build.gradle.kts:26-35）。
- **文件分享链接**：createShareLink 用「路径 hashCode 逐位映射 + 随机字符」生成短 id，冲突则追加随机位，过期时间 1 天/7 天/10 年三档（FileServiceImpl.kt:414-443），下载走 /s/* 由魔改 Tomcat 转发到 CoolDesktopShareHttpServlet 免认证直出文件（SystemConfiguration.kt:41-58, CoolDesktopShareHttpServlet.kt:18-30），每天 12 点定时清理过期链接与 180 天前的审计日志（DatabaseScheduled.kt:18-23）。
- **日志追踪（tail）**：tailStart 起一个 `bash -c tail -F -n 250 <path>` 进程逐行回调，输出推到按路径动态拼的主题 `/event/tail/$path`（FileServiceImpl.kt:396-407, Tail.kt:20-29）。

### 5.2 desktop-system：终端、命令模板与横切面

- **终端**：pty4j PtyProcess 起 /bin/bash（desktop-system/build.gradle.kts:10 依赖 pty4j 0.12.10），详见第 4 节。
- **命令模板**：CommandConstant 枚举集中管理 ssh-keygen、nohup java -jar、kill -9、tail -F、netstat/lsof 查端口六条模板（CommandConstant.kt:5-11），CommandImpl 执行。这类「模板集中一处」的做法比散落各处拼字符串好维护，但模板本身硬编码了 netstat/lsof 等非 POSIX 必备命令。
- **通知 AOP**：@NotifyWebSocket + CoolDesktopNotifyWebSocketAspect（第 3.2 节）。
- **审计 AOP**：@LogRecord 注解 + LogRecordAspect @Before 切面，把控制器参数名与值序列化后写入 sys_log 表（LogRecordAspect.kt:37-58），所有敏感操作（删除、上传、重置密码、装软件）都挂了注解（StaticResourceController.kt 全篇、CoolDesktopSystemController.kt:40-137）。配合 getSystemLog 分页查询接口构成操作审计闭环（CoolDesktopSystemController.kt:151-158）。
- **SSH 密钥管理**：configSecureShell 生成 PEM 密钥对（ssh-keygen -m PEM -b 2048，CommandConstant.kt:6），公钥追加到硬编码的 /root/.ssh/authorized_keys（CoolDesktopSystem.kt:59, 98-143），私钥/公钥/用户名存 H2 且被列为敏感配置不回传客户端（CoolDesktopSystem.kt:52-57）。**仓库内没有任何消费这三项配置的代码**，desktop-system/build.gradle.kts:7 声明的 jsch 依赖也没有任何 import（grep com.jcraft 命中 0 处源码）——推断这组功能是给「浏览器端/第三方应用直连 SSH」准备的半成品，或者消费者在前端闭源仓。README「所用语言及依赖」里列了 jsch（README.md:59），佐证原本规划过 SSH 直连终端。

### 5.3 desktop-database 的角色

就是一个零依赖的 H2 键值仓 + 日志表：无 ORM、无迁移框架、建表用 create table if not exists 的 CommandLineRunner（CooldesktopDatabaseTablInitialization.kt:18-27）、连接串不带认证（CoolDesktopDatabaseConfig.kt:20）。表只有四张（第 1.3 节）。它的价值不在技术含量，而在于示范了「桌面类单机产品用什么存配置/状态/审计」的最小方案。

### 5.4 对 SSH 远程桌面场景的参考价值判断

- 文件域：7shell 的 SSH 场景下传输通道大概率走 SFTP，cooldesktop 的「分片上传/HTTP 下载」协议本身用不上，但**分片校验、失败预检、异步任务 + WS 进度推送、目录并发枚举、图标/缩略图 UX** 都是可平移的交互设计。
- 终端域：7shell 的终端应走 SSH channel（shell/exec）而非本地 pty4j，但 xterm.js + 文本帧直通 + resize 消息的三段式结构是通用模式；它的定长数字 resize 协议是反面教材，应换成结构化 JSON 或 doOnResize 语义消息。
- tail 日志追踪：对 7shell 的「日志文件追踪」功能有直接参考价值，但按路径拼主题的做法要改（见坑清单）。
- jar 进程管理：对「管理远程 Java 应用」的 7shell 用户是潜在功能，Attach API 要求管理进程与目标进程同机同用户，7shell 客户端在本地 Windows 上跑不了对远程主机的 Attach——这条路在 SSH 场景下不可行，只能靠远端脚本（它自己也是 nohup + bash，Attach 只用来查 pid，JarUtils.kt:27-30）。

## 6. 安全模型

### 6.1 认证：闭源魔改 Tomcat 全局阀

认证不在 Spring Security，而是魔改 tomcat-embed-core：jar 内含 TomcatGlobalAuthenticationValve（9.3KB 主类）、TomcatGlobalAuthenticationHttpServlet（登录 Servlet，带 IPLimitTask/IpLimitMessage/IP 限流内部类）、TomcatGlobalAuthenticationPasswordUtils、TomcatShareFileHttpServlet（unzip desktop-lib/tomcat-embed-core.jar 类清单实测）。根 build.gradle.kts:100 注释「主要功能，全局拦截，进行登录」。登录页由 Tomcat 直接伺服（desktop-web/src/main/resources/tomcat/tomcat-index.html），密码框用 jsencrypt 做 RSA 加密提交（tomcat-index.html:5 引 jsencrypt.min.js）。

TomcatCallback 用 MethodHandles 反射调用闭源 jar 的两个静态回调把 Tomcat 世界接回 Spring：登录结果写审计日志（TomcatCallback.kt:50-66）、分享下载 Servlet 注入（TomcatCallback.kt:31-40）。密码存 ~/cooldesktop-work/password.conf 明文（TomcatGlobalAuthenticationPasswordUtils.kt:12-33），重置时强制转大写（CoolDesktopSystem.kt:158-161），README 声明默认密码 cooldesktop（README.md:75-80）。

免认证路径有两个：OpenUrlManager 维护的 URL 白名单（存文件 config/o_urls/config，OpenUrlManager.kt:11-42，应用安装时自动注册 urlExclude，ApplicationManager.kt:72）；/s/* 分享下载路径（SystemConfiguration.kt:47 注释「生产环境中由 tomcat 负责转发……免除认证」）。

### 6.2 WebSocket 层零鉴权

STOMP 握手的 determineUser 直接发随机 UUID 当 Principal（DesktopWebSocketConfigurer.kt:28-34），STOMP 消息处理不校验任何身份；终端 WS allowedOrigins("*")。整个 WS 面的安全性完全依赖 HTTP 层的 Tomcat Valve 把没有登录 Cookie 的握手请求拦在门外（推断：Valve 是全局的，SockJS 握手走 HTTP，未登录者连不上；登录后的 WS 会话无二次鉴权，任何已登录页面可以全量订阅所有主题）。没有按用户的主题隔离——广播语义本来也是「单管理员」假设。

### 6.3 会话与权限模型

单用户、单管理员、无角色权限分级。服务进程 root 运行（install.sh:45 User=root），文件 API 可以读写任意路径（只有 canRead/canWrite 检查，FileServiceImpl.kt:261-263），shell 执行接口直接跑任意脚本（StaticResourceController.kt:100-103）。这不是疏忽而是产品定位——它就是给有 root 的人用的管理工具。多用户隔离、容器隔离在这个项目里都不存在；唯一的「隔离」手段是魔改 Valve 的 IP 限流（防止爆破登录）。

值得记录的一个防御性细节：系统配置接口对敏感 key（SSH 私钥/公钥/用户名）做了「不返回、不允许直接写」的双向过滤（CoolDesktopSystem.kt:52-57, 81-85）。

## 7. 与 7shell 需求的匹配度分析

7shell 的需求：通过 SSH 连接到一台 Linux 主机，查看并操作它的**真实桌面**。逐条对照：

**根本不匹配的部分（先说清楚，避免错位借鉴）：**

- **画面层零匹配**。7shell 要的是 X11/Wayland 桌面的像素级渲染（截屏轮询或视频流），cooldesktop 对此没有任何实现——它的「桌面」是浏览器 DOM 自绘的应用壳（第 2 节）。想在 7shell 的桌面渲染上从它借鉴编码/传输/渲染技术，是没有东西可拿的。
- **承载通道不匹配**。cooldesktop 的所有流量（HTTP API + SockJS + WS）都是浏览器直连服务端 TCP 端口，没有 SSH 承载、没有隧道适配、没有对 NAT/防火墙场景的考虑（install.sh 直接在服务器上开 2556 端口）。7shell 若复用其协议，等于要自己补上「把 HTTP/WS 塞进 SSH 通道」的整层。
- **部署模型不匹配**。目标机要装 JDK 11+、root systemd 常驻 Spring Boot + H2（install.sh:39-53），这套依赖重量级且侵入宿主机。7shell 的 SSH 场景理想状态是零部署或一个轻量远端 agent；把 cooldesktop 整套搬过去显然不成立。它的部分能力（pty4j、thumbnailator、H2）甚至要求目标机有 Java 环境——7shell 的远端不能假设有 Java。
- **单用户 root 假设**。无多用户、无权限分级、全局单例剪贴板、WS 无鉴权（第 6 节）。7shell 若做多人/多连接管理，这套模型不能沿用。

**可对齐的部分（客观判断，按价值排序）：**

1. **消息协议骨架**：STOMP 主题 + JSON 消息体（subject/action/payload 三元组，WebSocketMessageBuilder.kt:7-28）+ 服务端推送收敛点（CoolDesktopEventAction.send 统一入口）+ 离线缓冲（5 条上限）+ 延迟发送 + 全员断开清理（CoolDesktopEventAction.kt:32-77）。7shell 桌面会话的消息路由（画面帧、窗口事件、剪贴板、通知）可以采用同构设计——主题分层、单一发送入口、断线清理钩子，这些和画面流是正交的。
2. **「提交任务 + WebSocket 推结果」的异步模式**：@NotifyWebSocket AOP 把「异步任务完成通知」做成声明式（CoolDesktopNotifyWebSocketAspect.kt:39-68），接口层提交即返回 taskId（StaticResourceController.kt:176-181）。7shell 的文件传输、压缩、长命令等耗时操作可沿用这个 UX 形态（实现上不用 AOP，7shell 是 Tauri 客户端不是 Web）。
3. **文件管理器交互设计**：目录一次请求全量属性 + 并发构建（FileServiceImpl.kt:173-212）、类型图标 + 缩略图（FileServiceImpl.kt:217-259）、服务端剪贴板语义（copy/cut/paste 三命令，ClipboardManager.kt）、分片上传的完整性校验与合并锁（FileServiceImpl.kt:129-168）。这些 UX 决策对 7shell 的 SFTP 文件管理界面有直接参考意义，只是传输通道换成 SFTP。
4. **终端链路结构**：xterm.js（前端渲染）+ 文本帧直通 ANSI（传输）+ PTY（后端）三段式，以及断开即销毁终端的会话生命周期（XterminalWebSocketConfigurer.kt:20-34, TerminalSocketAction.kt:36-40）。7shell 的 SSH 终端等价物是 xterm.js + SSH shell channel，结构同构。
5. **操作审计**：@LogRecord 声明式审计 + H2 分页查询 + 定期清理（LogRecordAspect.kt:37-58, DatabaseScheduled.kt:18-23）。7shell 若要「连接内操作记录」功能，这是最简参考实现。
6. **应用加载器思路**（仅在未来 7shell 做插件生态时有参考价值）：魔数识别应用类型、类加载器隔离、动态 bean/Controller 注册与反注册、按应用 id 加 URL 前缀隔离（第 2.1 节）。这个子系统复杂度高、闭源 jar 依赖多，7shell 短期不建议碰，但它证明了「单 JVM 内热插拔 Web 应用」在 Spring Boot 上可行。

**总体判断**：cooldesktop 与 7shell「Linux 桌面」需求的关系是「同为 Linux 远程管理工具，交互范式相近，但核心渲染技术线不同」。它验证了「Web 桌面壳 + 应用生态」这条路（值得学习交互与协议组织），不能提供「真实桌面画面传输」的任何经验。7shell 的画面采集/编码/传输需要参考的是 noVNC、xrdp、RustDesk、KasmVNC 这一类项目，cooldesktop 只能贡献外围（文件、终端、协议组织、审计）。

## 8. 精华点与坑/局限清单

### 8.1 精华点（值得学）

1. **统一推送收敛 + 离线缓冲 + 断线清理**：所有服务端推送走 CoolDesktopEventAction.send 单点；无订阅者时最多缓冲 5 条，订阅建立即冲刷；最后一个客户端断开时停掉所有 tail 进程（desktop-websocket/.../CoolDesktopEventAction.kt:32-77）。防推送风暴、防资源泄漏两个问题一起解决。
2. **声明式 WebSocket 通知**：方法上挂 @NotifyWebSocket(subject=..., action=...)，AOP 自动把返回值/异常转成 JSON 推给前端，业务代码零侵入（desktop-system/.../CoolDesktopNotifyWebSocketAspect.kt:39-68；用法示例 desktop-file/.../FileServiceImpl.kt:78）。耗时操作「提交即返回 + 推送收尾」的 UX 全项目一致。
3. **运行中 Spring 容器的应用热插拔**：自定义类加载器支持嵌套 jar（desktop-loader/.../EasyApplicationLoader.kt:215-229）、@Component 扫描注册进 defaultListableBeanFactory（同文件 234-265）、Controller 动态注册并自动加 /{applicationId} 前缀实现多应用路由隔离（desktop-system/.../RequestMappingRegister.kt:54-68）、卸载链完整（uninstall 方法 → 销毁 bean → 反注册 mapping → 删文件，EasyApplicationLoader.kt:141-157）、类加载器身份校验防同包名冲突（CoolDesktopBeanRegister.kt:54-58）。
4. **自定义二进制应用分发格式**：4 字节魔数区分类型（webmini 0x007913E / easyapp PK\x03\x04，ApplicationTypeDetection.kt:8-18），.webapp 格式「魔数 + JSON 头长度 + JSON + 资源 FilePackage」单文件分发带偏移定位（WebMiniApplicationLoader.kt:40-52），服务端按需解包 + 内存缓存（WebMiniApplicationWrapper.kt:14-22）。
5. **分片上传的并发安全合并**：目标存在性预检 → 分片落盘 → 「字节总和 == total」判完整 → ConcurrentHashMap 锁对象 + synchronized 单线程合并 → 合并后即清锁删目录（FileServiceImpl.kt:129-168）。并发上传同一文件时只有一个线程执行合并，其余直接返回。
6. **审计与通知双 AOP 横切面**：@LogRecord 在方法执行前记录参数到 sys_log（LogRecordAspect.kt:37-58），参数按类型分派转换器（MultipartFile 只记文件名等），配合每天 12 点的过期清理定时任务（DatabaseScheduled.kt:18-23）形成最小审计闭环。
7. **敏感配置双向过滤**：SSH 密钥等 key 既不返回给客户端也不允许通过配置接口写入（CoolDesktopSystem.kt:52-57, 81-85），接口层显式白名单思维。
8. **全局认证阀 + 免认证白名单**：认证收敛在 Tomcat Valve 一层，业务代码完全无感；需要免认证的路径走显式白名单注册（OpenUrlManager.kt:11-42、ApplicationManager.kt:72），还带登录 IP 限流（desktop-lib/tomcat-embed-core.jar 内 IPLimitTask 类）。

### 8.2 坑与局限（值得避）

1. **认证核心闭源、构建不可复现**：魔改 Tomcat 与应用定义 jar 都是仓库外预编译产物（desktop-lib/*.jar），copyLib 任务硬编码作者本机路径（build.gradle.kts:38-51），离开作者机器无法完整构建；安全审计只能靠反编译闭源 jar。
2. **密码明文落盘 + 重置强制大写**：password.conf 明文存储（TomcatGlobalAuthenticationPasswordUtils.kt:27-33），重置入口 uppercase() 静默缩小密码空间且用户不知情（CoolDesktopSystem.kt:158-161）；登录页 RSA（jsencrypt）只保护传输不保护存储。
3. **WebSocket 层零鉴权 + 全开 CORS**：握手 Principal 是随机 UUID（DesktopWebSocketConfigurer.kt:28-34），STOMP/终端 WS 不做任何身份校验，终端端点 allowedOrigins("*")（XterminalWebSocketConfigurer.kt:34），安全性 100% 押在 HTTP Valve 兜底上；WS 一旦换成非 Tomcat 容器或加直连路径就裸奔。
4. **SQL 字符串拼接**：sys_log 查询的条件构造器把参数直接拼进 SQL（`"$k=$v and "`、`'\'$value\''`，CoolDesktopDatabase.kt:104-143），logType/logLevel 来自请求参数（CoolDesktopSystemController.kt:151-158），存在注入面（H2 本地文件库 + 单管理员场景下危害有限，但模式不可取）。
5. **终端 resize 协议脆弱**：`setSize` + 四个定长 4 位数字段按固定下标切割（LinuxTerminal.kt:45-52），超过 9999 列/行或字段位数不足即错乱；`INIT_HOME_TERMINAL:` 前缀魔法串与普通命令共用一条通道（LinuxTerminal.kt:55-61），没有转义保护——目录名里含该前缀会被误吞。
6. **tail 主题直接拼用户路径**：`/event/tail/$path` 把任意文件路径编进 STOMP 主题（FileServiceImpl.kt:396-407），多客户端下主题互相可见且路径信息泄露给所有订阅者；路径变化（软链、重命名）也会让主题失效。
7. **全局单例剪贴板**：服务端只存一份 (action, path)（ClipboardManager.kt:10-15），多标签页/多会话互相覆盖，且粘贴是异步的、复制状态无过期。
8. **目录列表 1 分钟整体超时静默丢结果**：listDirector 的 CountDownLatch.await(1, MINUTES) 到点直接返回已收集部分（FileServiceImpl.kt:196-206），大目录（如 /proc 挂载点误入）下用户看到不完整列表却无任何提示。
9. **环境硬编码**：/bin/bash、netstat/lsof/tail、/root/.ssh/authorized_keys 全部写死（CommandConstant.kt:5-11、CoolDesktopSystem.kt:59），非 glibc 发行版、精简容器镜像、非 root 用户场景直接失效；Application.kt 非 Linux 强制退出（Application.kt:33-41）。
10. **H2 无认证无迁移**：连接串形如 `jdbc:h2:<path>`、不带凭据（CoolDesktopDatabaseConfig.kt:20），建表靠 if not exists（CooldesktopDatabaseTablInitialization.kt:18-27），无版本迁移机制——表结构演进只能靠手工兼容。
11. **SSH 密钥功能疑似半成品**：生成密钥写 authorized_keys、私钥入 H2（CoolDesktopSystem.kt:98-143），但仓库内无任何消费代码，jsch 依赖无 import（desktop-system/build.gradle.kts:7）；照着学之前要先确认其设计意图。
12. **前端闭源在独立仓**：本仓只有打包产物（README.md:88-94），窗口管理器实现细节（拖拽、快捷键、iframe 沙箱策略）无法在仓内核实，本报告第 3.3/4.3 节的前端结论均基于产物 bundle 关键词推断。

## 9. 对 7shell 的可借鉴清单

按「拿协议与思路、不拿代码与部署」的原则：

1. **消息协议组织**：主题分层枚举 + JSON 三元组（subject/action/payload）+ 单一发送收敛点 + 离线缓冲上限 + 最后断开者触发资源清理（CoolDesktopEventAction.kt:32-77）。7shell 的桌面会话协议（画面帧通道、事件通道、控制通道）可以直接套这个骨架，把 STOMP 主题换成 SSH 多路复用 channel 或自定义帧类型。
2. **耗时操作 UX**：提交即返回任务 id + 完成后推送结果 + 失败也推送（AOP 语义转成显式事件即可）（CoolDesktopNotifyWebSocketAspect.kt:39-68）。适用于 7shell 的文件传输、压缩、远程命令执行。
3. **文件管理器交互**：目录一次拉全量属性、类型图标内置、图片缩略图服务端生成、copy/cut/paste 服务端状态机、分片完整性校验（FileServiceImpl.kt 各节）。通道换 SFTP 后这些 UX 设计原样成立；分片上传若 7shell 要做大文件断点续传，「字节总和判完整 + 合并锁」仍可参考。
4. **终端三段式**：xterm.js + 文本帧直通 + 断开销毁的生命周期（XterminalWebSocketConfigurer.kt:20-34）。resize 必须用结构化消息（反向吸取 LinuxTerminal.kt:45-52 的教训），7shell 天然有 SSH pty-req resize 可用，不需要自定义协议。
5. **审计闭环**：声明式操作日志 + 分页查询 + 定期过期清理（LogRecordAspect.kt:37-58、DatabaseScheduled.kt:18-23）。若 7shell 需要「会话操作记录」，照此最小实现即可。
6. **安全设计正反面**：正面——认证收敛在单一拦截层、免认证路径显式白名单、敏感配置不回传（OpenUrlManager.kt:11-42、CoolDesktopSystem.kt:52-57）；反面——WS 层必须自带鉴权不能押注 HTTP 中间件（DesktopWebSocketConfigurer.kt:28-34 是教训）、密码不能明文落盘（TomcatGlobalAuthenticationPasswordUtils.kt:27-33 是教训）。
7. **不碰的部分**：真实桌面画面采集/编码/传输（它没有）、Spring 容器热插拔应用（短期不值得）、二开 Tomcat 认证（7shell 不是 Web 服务）、目标机 Java 依赖（7shell 不能假设远端有 JDK）。
