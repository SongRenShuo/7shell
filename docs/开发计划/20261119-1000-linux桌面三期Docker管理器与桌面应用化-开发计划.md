## 三、批次五：Docker 管理器 + 桌面应用化（本批）

### 3.1 架构决策

1. **引擎挂在会话自己的连接上**：GMSSH 的 Docker 管理器就是 docker-over-SSH。本仓 `container_connect` 只收 `protocol == container` 的会话；本批新增 **`desktop_engine_open(session_id)`**——协议限 `linuxDesk`，`Runner::Ssh` 直接用**该会话已建立的 carrier**（与 trash/文件窗口同一条连接，零新增连接），runtime=Docker，连接 id `desktop-<uuid>`，幂等（重复打开返回既有 id）。断开复用既有 `container_disconnect`，其余容器命令（list/inspect/stats/logs/exec/files/images/action）全部原样复用。
2. **窗口承载既有工作区**：桌面新增「Docker」门（图标+启动器瓦片，tone 蓝色系），窗口内承载 `<ContainerPane>`——容器工作区不是新写的界面，是被桌面窗口挂起来的既有组件。容器 tab 加 `windowed` 标记（与 terminal 同一机制），标签条不画、关窗即 `closeTab`（→ 引擎断开）。
3. **传输管理器窗口**：GMSSH 的上传管理器对位——桌面新增「传输」窗口承载既有 `TransferPanel`，kind `transfers`，无 tab、无连接。
4. **policy**：容器启停/删除走既有 `container_risk` 矩阵与审计，无新动词。

## 七、风险

1. **容器动作是破坏性动作**：真机验证只读（list/stats/logs/inspect/images）；启停/rm 走 UI 验证时只对**无状态测试容器**操作，或仅验证确认对话框弹出即取消。
2. **连接生命周期**：桌面关窗必须断开引擎，防连接泄漏；窗口最小化不断开（与终端同语义）。
3. **长流背压**：容器日志与批次六 tail 是持续流，窗口隐藏时暂停拉取（沿用监控面板「没人看就不采样」的纪律）。
4. **宿主差异**：docker 版本差异（29.9.3 实测可用）；nerdctl/namespace 路径不在本批（桌面只对 docker）。

## 九、批次六车道契约（2026-11-19 同日启动）

### 9.1 范围与裁定

- **转发管理器窗口**：运行时转发。核心已有 `TunnelHandle` / `tunnels()` / `close_tunnel()` / `bring_up_forwards()`，缺的只是「运行时加一条」：`tunnel_open(session_id, request)`——复用会话 carrier 的 `SshSession::forward_local / forward_dynamic`，注册进既有 tunnels 注册表（`OpenTunnel` 原样，含 connections 计数），`tunnel_runtime_stop(id)` 复用 `close_tunnel` 路径。请求体即 `LocalForward` 的序列形（无 id）。policy 新规则：`tunnel.open` = Caution（绑定地址非环回 → Ask，GMSSH 的「允许公网访问需确认」对位）；`tunnel.stop` = Caution。

- **批量执行窗口**：BatchPanel 无 props，直接进窗口（kind `batch`，单实例）。

## 十一、虚拟滚动评估（2026-11-19，批次七性能车道）

### 11.1 结论先行

**文件窗口的虚拟滚动已经在场，不需要再做。** 批次五的 FileBrowser 落地时就是窗口化渲染（`lib/files/window.ts` 的 `rowWindow`：只画可视区 + `OVERSCAN_ROWS=6` 行，首尾各一个撑高 `<li>` 替身撑住滚动条），本车道实测确认它在 2000 与 5000 条目下 DOM 规模恒定。「虚拟滚动评估」这一项应直接销项，无遗留工作。

### 11.2 实测读数（happy-dom，`FileBrowser.perf.spec.ts`）

| 目录规模 | 画出的行 | 面板 DOM 节点总数 | 挂载耗时 |
|---|---|---|---|
| 2000 条 | **40 行** | **552 节点** | 123~170ms |
| 5000 条 | **40 行** | **552 节点** | 123~170ms |

- 行数与节点数在两档规模下**逐字节相同**：目录大小不影响 DOM，只影响排序一次的 CPU（`orderEntries` 的 O(N log N)，毫秒级）。
- 滚动到最底（scrollTop=400000）后再量：行数仍 ≤ 40、节点数不变。
- 40 这个数来自无布局环境（happy-dom 报不出行高，走 `UNMEASURED_ROWS=40` 的兜底档）；真机 WebView 里行高量得出来，画的是「视口 ÷ 行距 + 2×6 过扫」，比 40 更少。

### 11.3 打算之外的顺带读数（同一批规格，`WorkbenchPane.perf.spec.ts`）

- **图标拖拽**：桌面上限 24 个快捷方式（`MAX_DESKTOP_SHORTCUTS`）+ 11 扇系统门 = 35 图标，10 轮完整拖拽序列（每轮 2 次悬停停靠）合计 **~70ms**，**零元素重挂**（逐图标元素身份逐一比对通过），网格节点数拖前拖后一致。`dropIcon` 整组重建 order 数组 + `icons` computed 重建列表在这个量级毫无压力，已在 `dropIcon` 上方留实测预算注释，规格作为回归守卫常驻。
- **keep-alive**：终端/Docker/日志/文件/传输/批量 6 窗全开 389 节点，全部最小化后 371 节点、6 个应用根**原元素仍在**（最小化是 transform 折叠不是卸载）；日志窗口最小化即关流（`fileTailClose` 被调），藏起来的窗口再来行也不进缓冲（`WorkbenchTailWindow.spec` 新增此用例）。

### 11.4 遗留建议

- 不做「per-500 行 chunk 懒渲染」，也不做第三方虚拟化引入——现有 `rowWindow` 已覆盖，新依赖违反本批约束。
- 唯一可选的后续（不紧迫）：真机对 ≥1 万条目目录实测一次滚动流畅度，把真机行距与过扫读数回填本节；规格守卫已把结构性上界钉住，真机只差一行读数。
